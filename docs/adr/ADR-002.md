# ADR-002: Interface Fluida com Mutação In-Memory

> Status: Aceito (retroativo) | Data: 2026-10-13
> Decisores: Heliomar P. Marques | Substitui: n/a
> Relacionados: src/LinqPHP.php

## Contexto e forças
A sintaxe do LINQ (.NET) se destaca pela expressividade ao encadear operações declarativas sobre sequências de dados (`from(data)->where(...)->groupBy(...)->select(...)`). 

No PHP, implementar encadeamento de métodos (Fluent Interface) sobre matrizes de dados em memória envolve um trade-off clássico entre imutabilidade (instanciar um novo objeto contendo uma cópia do array a cada operação) e mutação in-place (atualizar a propriedade interna do próprio objeto e retornar `$this`).

Como a biblioteca foi projetada para lidar com relatórios e volumes de dezenas a centenas de milhares de linhas (conforme os testes de estresse de até 100.000 registros), a duplicação contínua de arrays na memória sobrecarrega severamente o garbage collector do PHP.

## Critérios de decisão
Pegada de memória (memory footprint), velocidade de processamento de pipelines longos, simplicidade e elegância da sintaxe.

## Decisão
Implementar uma interface fluida com mutação interna do estado em memória: cada método intermediário (`where`, `join`, `groupBy`, `select`, `distinct`, `orderBy`, `take`, `unionAll`) transforma a propriedade privada `$this->data` in-place e retorna `$this` (`self`).

A extração dos dados é feita através de métodos terminais explícitos: `toArray()` para o array processado ou `toObject()` para um objeto contendo os dados e telemetria de performance.

## Alternativas avaliadas

| Opção | Prós | Contras |
| :--- | :--- | :--- |
| Imutabilidade estrita (novas instâncias a cada chamada) | Sem efeitos colaterais caso a mesma variável intermediária seja reutilizada; modelo conceitualmente puro | Explosão de alocação de memória RAM e lentidão significativa de garbage collection em coleções grandes (10.000+ linhas) |
| Funções puras / pipelines procedurais | Sem estado | Sintaxe verbosa ou aninhada (`order(group(filter($data)))`), distante da ergonomia do LINQ |
| Lazy Evaluation via Generators (`yield` / `Iterator`) | Avaliação sob demanda de itens; potencialmente útil para streams contínuos ou leitura linha a linha | Incompatível com operações de conjunto globais (`groupBy`, `orderBy` multicritério, `join` FULL/RIGHT) que exigem a coleção indexada completa em memória; overhead de chamadas de generator em loops internos reduz a performance frente a arrays nativos |
| **Mutação interna com retorno de `$this` (escolhida)** | Menor consumo de RAM, altíssima velocidade em benchmarks, código limpo e fluido | Reutilizar uma mesma instância atribuída a uma variável causará mutações acumuladas inesperadas |

## Consequências
- Positivas: consumo de memória linear e previsível; velocidade máxima comprovada nos benchmarks do projeto; legibilidade de código idêntica à sintaxe do LINQ.
- Negativas: instâncias não são imutáveis; fluxos que exigem bifurcações a partir de um mesmo ponto devem instanciar novas consultas explicitamente via `LinqPHP::from($origem)`.
- Avaliação de Lazy Evaluation / Generators: descartada formalmente em favor do alto desempenho com arrays nativos in-memory. Palavras-chave residuais (`iterator`, `yield`) removidas do `composer.json`.
